Permission, concurrency, and revocation walkthrough
  1. Private note: use Alice's key to create a note. Copy its ID before changing identity, because switching clears this page. Other users should receive 404 until it is shared.
  2. Permission demo: discover teams, get the note's sharing as Alice, then add Team A edit and organization read grants and replace sharing. Bob can edit through Team A; Carol can only read through the organization; Dana matches both and can edit. Only Alice, the owner of this note, can read/change sharing or delete it. Buttons never assume permission from a demo name.
  3. Stale save: load a note into editor A and clone its fetched snapshot to B. Save A, then edit and save B. B must receive 412 without losing its draft or original ETag. Load the latest version into the other slot to compare; preserve your changes, reload, reconcile, and explicitly save again.
  4. Preconditions: choose an omitted header for 428, or a manual value for stale/malformed tests. Examples: "1" (stale when an older version), W/"1", *, and "1", "2" (unsupported). Content, sharing, and deletion use the same note version, but each panel keeps its own fetched ETag.
  5. Revocation: use independent tabs for Alice and Bob. Load Bob's editable snapshot, then replace sharing with empty grants as Alice. New reads by Bob must return 404; his old save must not succeed (404 after revocation, or 412 if an authorized save races with the version change). Already returned content cannot be recalled.
  6. Atomic validation: edit sharing JSON to include a duplicate grant, unknown team, or invalid audience. A rejected replacement must leave sharing and version unchanged. Reload to verify. Use limit/offset and next/previous to check access-filtered paging and absence of duplicate notes for Dana.
